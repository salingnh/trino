# Search execution and query-shape hardening

## Phase-start architectural audit

P1.4 and P2 extend the existing Remote Predicate IR, table handle, translation
enforcement and connector-scoped diagnostics. They do not introduce another
predicate planner, residual model, or metrics pipeline.

`SearchExecutionStrategy` owns a remote pagination context. `SearchExecution`
owns consumption, LIMIT termination, cancellation, failure accounting and
idempotent cleanup. Scroll and PIT implement the same contract. The page source
only decodes documents returned by the execution. P2 early termination uses this
contract without knowing the pagination mechanism. A response decoder converts
transport JSON into the existing `SearchDocument` model; alternative decoders do
not change column decoding or SQL NULL/array semantics.

Scroll remains the default and compatibility path. PIT is opt-in and must preserve
shard restriction, query, projection, sort, stable tie breaking and the latest PIT
identifier. A failed/expired context fails the query; reopening it would silently
change the snapshot. Never switch strategy after rows have been returned.

Normal exhaustion and pushed LIMIT close resources immediately, without counting
as cancellation. An early downstream close counts cancellation. Decode, fetch and
open failures close owned resources without masking the original exception.
Retries remain in the existing bounded HTTP backpressure layer.

Statistics render the authoritative handle IR only when enforcement is exact.
Candidate/approximate filters retain conservative unknown statistics. Statistics
and mapping requests use per-request transport timeouts without backpressure
retries; statistics searches also carry a server-side query timeout. Large matched
document counts prevent per-column scans, not the initial exact-count work. These
controls are not a hard end-to-end planning or total server-work deadline.
No cache or configurable composite page size is added without measurements.
Aggregation has only one execution mode and needs no speculative strategy layer.

## Validation gates

- HTTP-backed lifecycle tests: open, pagination, latest context, LIMIT, exhaustion,
  early/repeated close, decode/fetch/cleanup failure and unchanged diagnostics.
- Response-decoder equivalence on nested values, arrays, missing/NULL, timestamps,
  binary, raw JSON, sort tokens and non-ASCII source bytes.
- ES7/ES8 correctness across predicates, projections, LIMIT/TopN, aggregation and
  statistics; benchmark pagination and decoding before enabling optimizations.
- AirStyle, focused tests, full connector tests and clean Error Prone verification
  locally before any push; CI afterwards. No phase completion inferred from an
  earlier SHA.

P3 sample/join remains research-only as specified by the roadmap. No unproven
sampling or join semantics will be enabled to make a checklist appear complete.

## Independent-review closure evidence (2026-09-06)

The review identified correctness gaps that the earlier green gate did not cover.
The implementation now rejects rounded `scaled_float` mappings for TopN, grouping,
numeric metrics and source-value column statistics. COUNT of a scalar field remains
eligible because rounding does not alter presence. The ES7/ES8 Scroll/PIT suites
exercise colliding rounded values, NULL, deterministic secondary ordering, all four
numeric metrics and grouping, with result comparisons and fallback assertions.
A metadata test additionally requires `applyTopN` to return empty for every sort order.

Hit conversion failures are deferred while the streaming decoder drains valid JSON
to collect later context IDs. Both decoder implementations and HTTP-backed Scroll
and PIT ownership tests cover this case and require exactly one close of the latest
ID, no reopened query, one failure and no spurious cancellation. Syntax/truncation
failures still terminate parsing immediately. Streaming shares Jackson's hit-sequence
deserialization context and copies only the final hit's continuation token.

Statistics tests now exercise actual per-column collection below the document
threshold, enforce the column limit, compare the IR in both search bodies, and cover
partial/missing responses, rounded mappings, mapping failure, mapping timeout and
column timeout. Available row estimates survive these failures. A provider-level
HTTP test verifies that dynamic filtering preserves the static predicate, projection,
sort and LIMIT in the emitted request and that LIMIT closes without another page.

The expanded full local gate passed 1,515 tests (835 executed, 680 inherited
unsupported-capability skips), with zero failures/errors, AirStyle, Checkstyle,
Error Prone compilation and plugin packaging. The full final-code repeat, including
the decoder follow-up and both benchmarks, also passes with the same counts
(8m59s, 2026-09-06 20:12 +07). The committed tree must pass the full command again
before push. PMD and SpotBugs remain skipped by the normal profile. No PR/CI result
is part of this local acceptance claim.

### Execution and planning measurements

The expanded run uses 50,000 documents, three shards, 100-hit pages, ES 7.17.27 and
8.11.3. Strategy order is reversed between versions. Each full scan returns every
ID once, with 505 search/page requests and 51,738,890 decoded source bytes.

| Version / strategy | Three full-scan rounds (ms) | Slow-consumer scan (ms) | Cancellation cleanup (ms) |
| --- | --- | --- | --- |
| ES7 / Scroll | 2428 / 1791 / 1741 | 62123 | 1.122 |
| ES7 / PIT | 1991 / 1778 / 1784 | 62222 | 0.922 |
| ES8 / PIT | 3048 / 2154 / 2049 | 62584 | 1.212 |
| ES8 / Scroll | 1875 / 1669 / 1714 | 62034 | 1.189 |

All four combinations pass zero-open-context checks after normal exhaustion,
LIMIT/TopN, cancellation and injected next-page failure. Failure measurements
(6.104–7.372 ms) include initial page acquisition and cleanup, not just failure
handling. Independent fresh-query recovery returns all 50,000 IDs; there is no
transparent replay of a failed snapshot. Existing HTTP failure tests separately
cover remote error responses and cleanup failures.

Both LIMIT and TopN with shard-local N=10 use three search/page requests and return
30 candidates (30,950 decoded source bytes): 99.4% fewer requests and 99.94% fewer
source bytes than the full scan. TopN candidates contain the exact global first
ten IDs. This measures decoded source bytes, not network compression or wire bytes.

Twenty warmed statistics calls per mode/version measure the entire metadata call,
including mapping lookup for per-column statistics. Across the two strategy runs:

| Version | Row-only median / p95 (ms) | Per-column median / p95 (ms) |
| --- | --- | --- |
| ES7 | 1.610–2.089 / 1.725–2.386 | 4.786–6.495 / 5.210–21.157 |
| ES8 | 1.505–1.806 / 1.794–1.956 | 4.522–5.698 / 4.865–7.327 |

Row-only mode uses 20 search requests; per-column mode uses 40 searches and 20
mapping lookups. Allocation across 20 calls is about 0.53–0.56 MB versus 1.59 MB.
These measurements establish the planning baseline; they do not justify adding
cache invalidation complexity or a new aggregation page-size setting.

`BenchmarkMemory` records measured-thread allocations and process-wide GC
counts/time. Heap reporting is the sum of heap-pool peak usages during each interval:
pool peaks need not coincide, so it is an upper bound, not a precise peak live set.
The benchmarks run with JUnit isolation; retained JVM state and ES/container warming
still affect timings. A 60-second renewal test is a bounded local longevity gate,
not a claim of hour/day-scale production soak validation. Defaults stay Scroll and
materialized decoding.

### Decoder measurements after allocation follow-up

The follow-up removes per-hit deserialization-context setup and per-hit sort-list
copies. Thirty focused correctness tests plus the opt-in benchmark pass with Error
Prone. At 10,000 hits, the measured allocation decreases from the initial streaming
117,863,311 bytes/page to 116,423,489 bytes/page (about 1.2%). Materialized decoding
still allocates less (115,786,537 bytes/page); there is no allocation-win claim.

| 10,000-hit page | Materialized (ms/page) | Streaming (ms/page) |
| --- | --- | --- |
| Materialized measured first | 67.432 | 64.489 |
| Streaming measured first | 71.747 | 64.779 |

This isolated run shows a modest workload-specific throughput benefit in both
orders, not a reliable general speedup. The full-suite repeat measured
67.419/72.887 ms (materialized/streaming) in forward order and 73.863/77.419 ms
(streaming/materialized) in reverse order: the winner changes. At 100/1,000 hits,
reverse-order warmed measurements also favor materialized. The measurement work
is complete, but broad performance benefit is unproven and promotion to the
default is explicitly rejected. Streaming remains opt-in; neither heap-pool peaks
nor these timings justify a production-wide optimization claim.
Reproduce with the command below; override
`elasticsearch.benchmark.documents` and `elasticsearch.benchmark.slow-seconds` for
larger datasets or longer soak runs without changing the fixture code.

## Historical implementation evidence (before independent review)

The complete module gate passed with 1,491 tests, zero failures/errors and 682
skips (680 inherited unsupported-capability cases, two explicit benchmark gates).
The final pre-commit gate, including subsequent hardening and both opt-in
benchmarks, passes with 1,498 tests, zero failures/errors and 680 inherited
unsupported-capability skips. AirStyle, Error Prone, ES7/ES8 integration, docs and
plugin packaging all pass. The committed SHA must pass verification before push;
the exact-SHA CI result is tracked separately on the PR.
Both ES7/ES8 PIT suites inherit the same full predicate/connector test hierarchy
as Scroll; their page size is 100 and their decoder is streaming. PIT/materialized
also passed both full suites before enabling streaming in those fixtures.

Two reproducible measurement entry points are opt-in, not timing assertions:

```bash
./mvnw -nsu -pl :trino-elasticsearch -Delasticsearch.benchmark=true \
  -Dtest=TestSearchExecutionBenchmark,TestSearchResponseDecoderBenchmark test
```

The strategy experiment loads 5,000 documents across three shards and checks exact
ID coverage without duplicates. Each strategy reads 5,103,890 source bytes with
54 search/page requests per round, plus its context management requests. Initial
ES7 timings were Scroll 1,026/679/398 ms and PIT 487/379/364 ms; ES8 timings were
Scroll 711/497/374 ms and PIT 409/386/322 ms. Order, warming, shared JVM heap and
Docker scheduling confound these small measurements: they do not justify changing
defaults or claiming a production-wide speedup. Logged heap endpoints are not peak
heap or allocation measurements. A further round delays consumption so each scan
takes over five seconds with a one-second keep-alive; both strategies on both ES
versions renew successfully and return every document.

The decoder experiment compares 100- and 1,000-hit pages in both execution orders.
For 1,000 hits a warmed reverse-order measurement was roughly 7.5 ms/materialized
versus 7.6 ms/streaming; other orders favored streaming. Streaming avoids retaining
the whole response tree but a universal speed/heap benefit is not established.
Both defaults therefore stay unchanged; both alternatives are explicit opt-ins.

P2 retains the fixed composite size (1,000) and adds no statistics cache. There is
no evidence here that another page size or a cache improves representative work.
Statistics uses request timeout, column limit and document threshold; see the
scope of those bounds above. Partial responses remain unknown, and metadata lookup failures preserve
the available row estimate. Aggregation has one mode and no remote cursor to free;
close ends local pagination and failures cannot accidentally retry the page.

PIT protocol references: [pagination](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/paginate-search-results)
and [context ownership](https://www.elastic.co/docs/api/doc/elasticsearch/v8/operation/operation-open-point-in-time).

## P3 disposition

No production sample or join pushdown is added. A document sampling algorithm must
first prove the requested Trino sampling semantics, including probabilities and
NULL/array handling; the roadmap intentionally leaves it research-only. Generic
joins remain engine-side with exact dynamic filters. Implementing either without
that proof would violate the existing architectural and correctness requirements.

## Response field-order hardening

A follow-up regression exposed a streaming cleanup gap: failure metadata before
`_scroll_id`/`pit_id` caused the decoder to throw before transferring context
ownership. Streaming now reads the complete valid envelope before rejecting
timed-out or shard-failed results. It still returns no partial page. Tests cover
both failure forms and both decoders, plus HTTP-backed PIT cleanup proving that
the latest ID is closed exactly once without reopening the query. Malformed or
truncated JSON still fails immediately; an ID that was never received cannot be
recovered by this client.
