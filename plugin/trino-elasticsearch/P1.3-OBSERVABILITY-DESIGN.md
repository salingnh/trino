### Diagnostics and lifecycle validation

The subsequent implementation closes the rendering, normalization, dynamic-filter
outcome, and JMX/debug-consumer gaps above. Normalization events extend the existing
immutable decision tree. Rendered filter counts and UTF-8 bytes are recorded by the
query builder used by scan, count, and aggregation paths, independently of planner
invocations. Remote response pages are distinct from Trino output pages.

HTTP-backed production page-source tests reproduced four lifecycle failures before
the fix. The scan now owns the initial scroll immediately, clears it once on early
close or failure, and consumes a response without a scroll ID only once. Decode and
paging failures are counted once; cleanup failure does not mask the original error.
`Cancellations` means downstream early close before observed exhaustion or a pushed
LIMIT, not proof of a user-cancelled query. This fixes existing resource ownership;
it does not introduce the P1.4 strategy framework.

The full module command `./mvnw -nsu -pl :trino-elasticsearch airstyle:format
-Perrorprone-compiler test` recompiled production and test sources and passed 830
tests with zero failures/errors and 340 skips, including both ES7/ES8 connector and
metadata suites. Focused tests also verify JMX map contents, immutable snapshots,
debug on/off equivalence, count success/failure, UTF-8 rendering, normalization

This document records the architectural contract for P1.3. It is scoped to diagnostics and accounting. Predicate, decoder, aggregation, and statistics semantics remain unchanged. The release audit also required fixing initial-scroll ownership and failure/close cleanup in the existing scan; it does not introduce a new pagination strategy or execution framework.

## Permanent abstractions consumed

P1.3 consumes, without replacing:

- `ElasticsearchPredicateTranslation` and its `Decision` tree.
- `ElasticsearchPredicateTranslation.Reason` as the planner semantic reason taxonomy.
- `ElasticsearchRemotePredicate` as the only remote predicate representation.
- `ElasticsearchTableHandle.remotePredicate` as authoritative planner-to-execution state.
- Existing Elasticsearch client/page-source lifecycle as event producers until P1.4 moves those producers behind the permanent execution lifecycle.

## New permanent abstraction

P1.3 introduces one connector-scoped diagnostics/accounting service. It is the single sink for semantic planner observations and remote-execution accounting.

```text
Permanent planner/execution models
        │
        ├── PredicateTranslation.Decision
        ├── Remote Predicate IR
        ├── DynamicFilterPlanner
        ├── DSL renderer
        └── client/page-source lifecycle
                 │
                 ▼
      ElasticsearchPushdownDiagnostics
        ├── structured event/reason taxonomy
        ├── semantic counters
        ├── request/resource counters
        └── immutable snapshots
                 │
          ┌──────┼────────┐
          ▼      ▼        ▼
        debug   JMX      tests
        logs   metrics
```

Logs and JMX are consumers of the same accounting state. No separate log-only instrumentation or parallel metrics pipeline is allowed.

## Event model

The diagnostics service must expose stable structured categories rather than parsing log strings.

### Planner categories

- DOMAIN
- ARRAY
- ANY_MATCH
- LIKE
- REGEXP
- PREFIX
- BOOLEAN_AND
- BOOLEAN_OR
- BOOLEAN_NOT
- UNSUPPORTED
- NOOP

### Outcomes

- EXACT
- PREFILTER
- APPROXIMATE
- RESIDUAL
- REMAINING
- UNSUPPORTED
- NOOP

`ElasticsearchPredicateTranslation.Reason` remains the detailed semantic reason. The diagnostics service derives the coarse category/outcome from the permanent decision tree and does not create a second predicate representation.

## Counters required in P1.3

### Translation/composition

- translation nodes observed
- exact nodes
- prefilter nodes
- approximate nodes
- residual nodes
- remaining/compatibility nodes
- unsupported nodes
- boolean AND/OR/NOT decisions
- array-membership decisions
- any_match decisions where the existing translator can distinguish them without a new planner representation

### Remote Predicate IR

- IR nodes rendered
- AND/OR/NOT nodes
- Term nodes
- Terms nodes
- total Terms values
- Range nodes
- Prefix nodes
- Regexp nodes
- MatchPhrase nodes
- MatchPhrasePrefix nodes
- Exists nodes
- enforcement wrappers

### Dynamic filtering

- dynamic filters received
- empty dynamic filters
- values received
- exact predicates pushed
- values compacted into Terms
- batches generated
- filters rejected by bounds/semantics
- estimated request bytes where already available from the planner

### Execution/accounting

P1.3 records counters only where the current code already has an authoritative observation point. P1.4 moves these producers behind `SearchExecutionStrategy` without changing the diagnostics API.

- search/open requests
- next-page requests
- count requests
- rows decoded
- source bytes decoded
- pages returned
- retry attempts observable in `BackpressureRestClient`
- cancellations where observable
- failures
- clear-scroll/close calls

No speculative counters may be invented where the current lifecycle cannot observe them reliably.

## Debug logging

Debug logs may render a structured event/snapshot but must not contain semantics that exist only in text. Turning debug logging on or off must never change planner or execution behavior.

## JMX

`ElasticsearchPushdownDiagnostics` is connector-scoped, singleton-bound, and exported through the existing JMX binder. JMX getters expose counters/snapshots from the same service updated by planner/renderer/execution producers.

## P1.4 continuity

P1.4 adds `SearchExecutionStrategy` and moves request/page/row/byte/retry/cancellation/failure event production behind that lifecycle. It reuses the P1.3 diagnostics service unchanged except for additive counters/events.

No P1.3 execution instrumentation may require removal when Scroll is adapted to the P1.4 lifecycle.

## P2 continuity

P2 LIMIT/TopN, aggregation, and statistics paths emit into the same diagnostics service. They may add query-shape labels/counters, but may not create separate accounting classes for each execution path.

## Explicit non-goals

P1.3 does not:

- change SQL predicate semantics;
- change EXACT/PREFILTER/APPROXIMATE decisions;
- alter residual handling;
- change `ElasticsearchTableHandle` serialization;
- refactor Scroll lifecycle;
- implement PIT/search_after;
- replace JsonNode hit decoding;
- change aggregation/statistics correctness policy.

## Implementation slices

### Slice A — permanent diagnostics core

- Add `ElasticsearchPushdownDiagnostics`.
- Add immutable snapshot/event types.
- Add decision-tree and IR traversal accounting.
- Export the singleton through JMX.
- Add focused tests proving deterministic accounting and no mutation of planner state.

### Slice B — planner and renderer producers

- Record the final P1.2 decision tree once per planner invocation.
- Record rendered IR characteristics at the canonical renderer boundary.
- Ensure repeated planner calls are accounted as separate planner operations, while each decision node is counted exactly once per recorded tree.

### Slice C — dynamic-filter producer

- Record received/pushed/batched/rejected dynamic-filter information from `ElasticsearchDynamicFilterPlanner`/page-source integration without changing filter semantics or bounds.

### Slice D — currently observable execution counters

- Record search, next-page, count, decoded row/source-byte, failure, retry, and clear-scroll signals at authoritative current call sites.
- Do not restructure the lifecycle; P1.4 owns that refactor.

### Slice E — cumulative gates

Focused tests first, then:

```bash
./mvnw -pl :trino-elasticsearch airstyle:format
git diff --check
./mvnw -pl :trino-elasticsearch airstyle:check
./mvnw -pl :trino-elasticsearch test
```

Then exact branch GitHub CI. P1.3 is not complete until cumulative ES7/ES8 connector behavior remains green and the roadmap is updated with exact validation evidence.

## Completion criteria

P1.3 is complete only when:

1. planner decisions and Remote Predicate IR can be diagnosed without parsing SQL or Elasticsearch payloads;
2. debug logs and JMX consume the same diagnostics state;
3. dynamic-filter accounting is bounded and semantic-preserving;
4. currently observable execution accounting is exposed without lifecycle refactoring;
5. P1.4 can move event production behind `SearchExecutionStrategy` without replacing the diagnostics API;
6. no predicate, residual, serialization, or execution semantics change;
7. focused, module, ES7/ES8, formatting, Error Prone, and GitHub CI gates are green.
